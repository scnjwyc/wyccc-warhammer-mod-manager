# v20 魔改安装包分析与 MOD 启动排障移植

分析日期：2026-09-27。输入为用户提供的 `管理器魔改版v20_开关安装包.zip`。

## 结论

这是一个替换整个主程序的魔改版，不是可单独加载的插件。程序中确实有 MOD
启动崩溃分析、二分试启动、连续排除和排查历史；随包 README 只介绍体型血量
倍率修复，没有完整描述 EXE 的功能。

本次将 MOD 启动排障重写为本体的独立服务，并增加界面入口、六种语言、测试和
可恢复的历史。没有运行安装脚本或魔改 EXE，没有覆盖已安装管理器，没有执行发布打包。

## 安装包实际做什么

ZIP 只有三个文件：

| 文件 | 大小 | 用途 |
| --- | ---: | --- |
| `install_or_uninstall.bat` | 3,371 字节 | 开关式安装和还原 |
| `WycccModManager_v20_modded.exe` | 60,360,768 字节 | 完整的 PyInstaller 管理器 |
| `说明_README.txt` | 1,961 字节 | 安装说明及体型血量修复介绍 |

EXE SHA-256 实测为
`eb4af6c083447dca93f0e3de3b2e2bbe044e9810619e854d1154ab23ea03fbd3`，与说明一致。

安装脚本会关闭同名管理器进程，将当前 EXE 备份为
`Wyccc's Mod Manager.exe.bak_official`，复制魔改 EXE 覆盖正式 EXE，并写入
`.wmm_modded_v20_installed.flag`。再次运行会还原备份并删除标记。脚本不直接修改
订阅或播放集；运行后的魔改管理器具有自己的状态写入逻辑，不能据此认为整个程序只改 EXE。

## 检测功能的实现证据

静态读取 PyInstaller CArchive 和 PYZ，并使用 xdis 解码 Python 3.13 字节码。
没有导入或执行解出的程序模块。CArchive 含 1,183 项，PYZ 含 745 个模块。

新增模块包括：

| 模块/函数 | 字节码中可确认的行为 |
| --- | --- |
| `backend.crash_diagnostics.diagnose_launch` | 对照启动清单、`logs/modified.log`、崩溃转储和退出标记，列出未装载项 |
| `read_dump_exception` | 从 `.mdmp` 异常流读取异常码、地址、参数 |
| `BisectPlanner.next_test/apply` | 完整组合基线、折半、单独启用验证和移除后反证 |
| `GameProbe.run` | 反复真实启动游戏，观察日志、进程、转储和 CA 报错窗口，结束本轮进程 |
| `MaxLoadResolver.resolve` | 从弹框正文提取 Pack 名，或通过二分找出候选，连续排除后再启动 |
| `MaxLoadHistory.record_run/restore_plan` | 保存被排除项和启用顺序，支持历史恢复及跨次序的 `known_bad` 名册 |
| `API._maxload_disable` | 在连续排除过程中修改当前播放集 |
| `API._remember_launch` | 持久化实际启动清单和时间，供下次诊断 |

前端编译产物中同时包含“启动排障”“二分排障”“排查全部冲突”“排查历史”入口及对应 RPC。

日志比对的关键点是：Movie Pack 不应计入 `Mod:` 日志的应加载数量；依赖可改变实际
装载顺序，因此应比较集合，而不能简单认定最后加载项的下一个包有错。

这套功能排查的是启动阶段。它不能静态证明所有数据库、Lua、存档或战斗逻辑都没有问题。

## 原版判定中不宜照搬的部分

1. `GameProbe.run` 有“观察窗口内未崩溃（未捕获到主菜单痕迹，进程存活）”成功分支。
   `_reached_main_menu` 只判断 `mp_log.txt`、`lua_mod_log.txt`、`script_log_*.txt` 的时间，
   并不读取证明主菜单已经出现的内容。
2. `MaxLoadResolver._bisect_one` 接受 `confirmed`、`combo`、`multi` 候选，而后续历史会
   累积 `known_bad`。组合冲突和独立坏包的证据强度不同，更新 MOD 后历史也可能失效。
3. CA 弹框中出现多个 Pack 名不等于这些包全部损坏；一次性排除所有名字可能过度缩减列表。
4. 简单折半没有依赖成组机制，会制造“子 MOD 开着、前置被关掉”的新失败。
5. 逐次排除并不能证明得到数学意义上的最大可加载集合。

## 本体中的使用与行为

底部工具栏打开 **MOD 启动排障**，可选择“定位一组冲突”或“连续排除并验证”。

- 使用当前已启用列表，保持顺序。依赖按组测试，同名 Pack 歧义和缺失依赖会在开始前提示。
- 每轮使用唯一的 `wyccc_diagnostics_<id>.txt`，不调用会保存播放集的正常启动流程。
  启动清单采用游戏对应编码和 CRLF，结束后删除本轮临时清单。
- 原始 MOD 参与测试，不生成管理器数值或兼容性补丁。Movie 包及其依赖保持为固定背景。
  最后一轮额外使用结果列表的真实搜索目录，验证移除外部目录后的自动加载环境。
- 新转储或当前试验进程的崩溃窗口可自动判失败。进程存活、日志时间推进和超时都不当作成功。
  到达主菜单后由用户确认成功；没有转储的退出也需要用户判断。确认会结束当前试验进程。
- 先复现完整组合，再测试固定背景；缩减同时检查子集和补集，以覆盖组合冲突。
  候选必须复测失败，剩余列表必须实际试启动成功，才出现“应用已验证结果”。
- 连续排除只形成建议列表，完成前不改播放集。应用和恢复都要求界面确认。
- 排查中阻止切换游戏、修改 MOD 和普通启动；关闭管理器会请求取消。低消耗页面不会在试验中
  把进度界面替换掉。进程清理限制在本轮启动后观察到、并且仍与目标游戏匹配的进程。
- 历史按游戏保存，保留原列表和结果列表，不建立“永久坏包”名册。切换播放集、更新文件、
  改变游戏路径或 Movie 包环境后，历史结果必须重新验证。只改变顺序时可显式恢复历史顺序。
- 重启不会自行继续启动游戏；未完成的会话显示为“中断”。

后端分别位于 `crash_diagnostics.py`（证据读取）、`mod_diagnostics.py`（试验与缩减）、
`diagnostics_api.py`（当前游戏/播放集接入），通过现有 API allowlist 暴露。
前端入口在 `App.vue`，面板为 `ModDiagnosticsModal.vue`，文案在 `diagnosticsLanguages.js`。
