# 新订阅 MOD 的工坊信息刷新优化

## 结论

新增一个 MOD 原先会刷新全部已安装工坊项目，并在在线请求返回后才把本地扫描结果交给界面。当前改为先显示本地结果，只补充新增项目；基础信息与当前语言内容合并为一次 Steamworks 查询。网络等待与本地扫描使用不同的锁，同一时间下载的新 MOD 可以继续显示并合并排队获取信息。

本机 305 个 MOD、290 个工坊项目的隔离复测中，新增一个项目的在线补充从 35.040 秒降到 1.493 秒，约减少 95.7%。最终本地扫描耗时 0.871 秒，不需要等在线补充结束才显示列表。该数值是本次网络和缓存条件下的测量，不能视为所有玩家的固定耗时。

## 原因与改动

1. `refreshModsInBackground` 原先串联 `scan_mods(false)`、`scan_mods(true)`，第二次扫描完成后才更新列表。现在立即应用本地扫描，再异步补充新工坊 ID。
2. `scan_mods(true)` 原先请求所有工坊项目的英文信息。新增项目改用限定 ID 的 `refresh_workshop_metadata`；全量手动刷新和旧 RPC 入口仍可使用。
3. 新增项目的英文信息原先走公开 HTTP 接口，实测仅此阶段占 33.096 秒。现在用现有 Steamworks 接口一次查询英文和界面语言，正常情况下不请求 HTTP；客户端失败或缺失英文结果时保留 HTTP 回退，失败的客户端查询不会在同一轮被重复执行。
4. 没有译文的成功响应原先被标记为失败且没有重试冷却。本机旧缓存中有 261 条这样的记录。现在视为有效英文回退，并兼容旧缓存；真正查询失败仍遵守重试冷却。
5. 后台回复会检查游戏上下文与文件修订号，并保留当前启用顺序，避免慢回复覆盖更新的列表或玩家操作。
6. 启动时自动刷新先筛选有效缓存：基础信息缓存六小时，语言与依赖缓存二十四小时，作者沿用七天成功缓存及三十分钟失败冷却。最近已返回不可用结果的项目也遵守基础缓存期限；手动按钮仍可全量刷新。覆盖了启动器关闭后新订阅再重新打开的路径。

## 测量方法

读取运行中启动器的设置、缓存，复制到仓库内的临时目录。删除副本中的一条已安装工坊项目记录，模拟新订阅后的首次信息读取。先运行本地生产扫描路径，再使用真实 Steam HTTP/Steamworks 查询。原始 MOD、运行中启动器的缓存和设置未写入，临时目录已自动清理。

优化前请求全部 290 个项目，英文请求 33.096 秒，在线补充总计 35.040 秒。仅限制为新增项目后仍需 11.192 秒，其中 HTTP 为 9.536 秒。最终合并客户端查询后总计 1.493 秒，标题和作者信息均可用，HTTP 调用为 0，副本中其余 359 条项目记录保持一致。该模拟复用了已有作者缓存，首次遇到新作者的解析仍可能额外耗时，界面可以继续操作。

启动时的缓存筛选也使用真实缓存副本验证：290 个已安装工坊项目全部有效时，待查询数为 0；仅删除一个项目缓存后，待查询数为 1，且正是被删除的项目。

各阶段原始测量见 [measurements.json](measurements.json)。这不是重新订阅 Steam 项目或运行已发布 EXE 的实测；源码尚未打包发布。

## 验证

- 新 MOD 下载后的运行时修订变化 → 本地扫描 → 在线请求延迟：修改前稳定失败，列表为空；修改后真实 App/ModList 组件已显示新 MOD，可以点击启用，在线回复后启用状态保留。
- 在线请求延迟时再次出现新 MOD：继续扫描和显示，只对新增 ID 排队补充信息；旧修订回复不删除新 MOD。
- 真实 API 调用验证指定 ID、去重、过滤未安装 ID、完整本地结果、网络期间并行本地扫描，以及游戏切换后丢弃旧结果。
- 验证英文回退结果复用、旧缓存兼容、英文与中文合并查询，以及客户端失败后的 HTTP 回退。
- 后端工坊、扫描、RPC、桥接与扫描冲突回归 127 项、25 个子用例通过；前端完整回归 302 项通过（`--maxWorkers=1`），生产构建、Ruff 和 `git diff --check` 通过。

首次较广的后端测试中，4 个强制更新测试被本机正在运行的游戏触发了既有保护。这些测试预期游戏未运行；在测试环境隔离 `backend.api.is_game_running` 后通过，未关闭或修改用户的游戏进程。

一次并行前端回归中，未修改的单位编辑器 2050 行分页测试触及既有 5 秒超时；独立重跑耗时 3.11 秒并通过，随后使用单工作进程的完整回归全部通过，未改动该测试或其超时设置。
