# 启动器内置 Pack 安全与启动可靠性检查

检查日期：2026-10-03。对象：当前 `main` 工作区、历史 1.1.5/1.1.6 源码，以及本机安装版生成的 Pack。用户补充：反馈是游戏打不开，截图来自 1.1.6 以前的版本，无法确认两个文件的完整名称。

本轮先完成源码审计与隔离复现，再修复发现的运行时 Pack 风险并把回归检查纳入发布验证。没有写入真实游戏 Data 或安装版启动器目录，也没有启动、关闭游戏。此前 schema 和工坊刷新任务的改动保持原状。

## 结论

审计确认了两处当前源码缺陷，并已在 1.1.9 修复：改名副本不再被作为普通 MOD 启用或重复加工；单位数据补丁现在会复核生成前后的来源指纹、变化时重试一次，连续变化就中止生成。另补上了运行时 Pack 目标指向符号链接时的目录边界处理。另有一类符合旧版反馈的启动阻断：1.1.5 不能读取合法的 CA LZMA 压缩表；该解压支持已在 1.1.6 加入。

目前不能把这些结果直接认定为玩家反馈的全部原因。没有原截图完整文件名，也没有对应玩家的日志或失败现场，不能确定截图中是同功能副本，还是游戏数据补丁、单位数据补丁及订阅标记分别存在。

本机当前没有发现两份游戏数据补丁。现有该补丁的 4 张表、1844 行解析和重建检查通过，表版本与安装游戏匹配，非目标字段保持原字节。修复后的隔离审计通过；本次完整验证为后端 518 项通过、1 项跳过和 191 个子用例通过，前端 302 项通过。

## 内置文件的范围与加载方式

| 文件 | 实际用途 | 写入与清理 |
| --- | --- | --- |
| `!!!!wyccc_game_data_patch.pack` | 全局规模、招募容量和友军伤害覆盖 | 运行时目录生成，启动前复制到游戏 Data；无修改时清理固定文件 |
| `!!!!wyccc_unit_data_patch.pack` | 玩家逐单位修改、禁用及相关数据克隆 | 同上；读取保存的逐单位编辑 |
| `!!!!wyccc_runtime_options.pack` | 跳过片头、脚本日志、自定义战斗权限 | 每次启动按设置生成；无选项时清理固定文件 |
| `!!!!wyccc_dynamic_ror_compatibility.pack` | Nanu 动态 RoR 兼容数据 | 开启且有有效结果时生成；关闭或零结果时清理 |
| `!!!!wyccc_variant_selector_patch.pack` | Variant Selector 的角色外观注册 Lua | 订阅标记、设置及框架满足条件时生成；条件不满足时清理 |

五种运行时文件通过同一个 PFH5 写入器生成，默认类型是 **Mod，类型值 3**。它们通过启动清单加载；仅仅放在 Data 中不等于被当前启动加载。生成写入使用临时文件、`fsync`、`os.replace`；部署到 Data 也采用临时文件替换，临时文件以 `.tmp` 结尾。

四种有状态补丁在运行时目录记录输入指纹与输出 SHA-256；启动选项 Pack 每次重建。内部项按固定文件名从普通启用顺序中排除，最后由启动流程插入。

以下文件是订阅/功能标记，不能按运行时补丁的规则一并删除：

- `wyccc_dynamic_unit_size.pack`、`wyccc_dynamic_no_friendly_fire.pack`、`wyccc_dynamic_unit_cap.pack`。
- `wyccc_dynamic_units_modify.pack`、`wyccc_variant_selector_patch.pack`。
- `wyccc_nanu_rors_patch.pack` 属于已识别的内部功能项，不是上述五种运行时输出。

本机 `wyccc_dynamic_units_modify.pack` 只有 RPFM 保留元数据，`wyccc_variant_selector_patch.pack` 只有功能 JSON，没有游戏 DB 表。界面把订阅标记和实际单位数据补丁都显示为“单位数据修改”，所以出现两个类似名字本身不能证明有两个相同补丁。

检查了 0.6.0、0.8.0、0.9.7、1.1.0 及当前相关源码，游戏数据补丁固定名均为四个感叹号的 `!!!!wyccc_game_data_patch.pack`，没有找到这些版本自动换名生成第二份的证据。

## 已复现问题

### F01 — 1.1.9 已修复：改名副本不会重复加工或进入启动清单

位置：`backend/constants.py:66`、`backend/api.py:3237`、`backend/api.py:3266`、`backend/api.py:3152`、`backend/start_options.py:609`。

改动前内部识别只依赖固定文件名。将生成的补丁复制为 `!!!!wyccc_game_data_patch (1).pack` 后，扫描会把它当成普通 MOD。1.1.9 的扫描器读取 Pack 索引中的保留表名和脚本标记来识别启动器生成的 Pack；无论用户是否显示隐藏 MOD，它们都会从播放集启用顺序和补丁数据来源中排除。启动器仍只部署一个标准文件名的生成结果，不删除改名副本，以保留原文件供用户检查或恢复。

复现步骤和结果：

1. 原版单位 100 人，设置 2 倍，通过真实 API 启动路径生成 200 人补丁；实际进程调用已替换为测试桩。
2. 在隔离 Data 复制该补丁为上述改名副本，并启用副本。
3. 使用同一隔离路径验证 1.1.9：改名副本被标记隐藏，不进入补丁来源；标准补丁保持 **200 人**，启动清单只引用标准文件。
4. 把设置恢复为 1 倍再启动，标准补丁移除，改名副本仍保留在 Data，但不进入启动清单。

该修复覆盖了隔离复现的“双份同功能文件”场景；副本由审计脚本创建，不代表启动器曾在玩家机器上自动复制生成文件。识别依赖启动器生成时使用的专属 DB/脚本标记和完整片头影片清单，不使用宽泛的文件名前缀。

### F02 — 1.1.9 已修复：单位数据来源变化时不再使用过期补丁

位置：`backend/unit_data_state.py:223`，特别是生成后的 `273–312` 行；`backend/api.py:1512`、`backend/api.py:1532`。

改动前，单位数据补丁只有生成前快照，无法覆盖来源 Pack 读完后、补丁生成结束前发生的 MOD 更新。1.1.9 现在会在生成后重新读取来源并比对内容指纹；来源变化时重建一次，连续两次变化则删除未验证输出并返回错误，因此启动流程不会继续使用旧快照生成的补丁。

隔离复现使用真实单位数据生成器，在它生成后、返回调用者前原子更新来源 MOD，模拟 Steam 更新：

- 玩家只修改近战攻击为 50。
- 生成时来源单位引用 `wyccc_audit_entity_old`，额外生命为 1111。
- 来源更新后改为 `wyccc_audit_entity_new`，删除旧实体记录，额外生命为 2222。
- 改动前 API 会继续启动，输出保留生命 1111 和已删除的旧实体引用。
- 1.1.9 检出来源变化后重试；生成的补丁使用新实体引用和生命 2222，同时保留玩家的攻击 50 修改。

这证明改动前输出与当前 MOD 不一致。1.1.9 的隔离用例确认一次变化会成功重试，持续变化会中止且不留下旧补丁。本轮没有让真实游戏加载旧版坏样本，因此不把它写成已复现的原生游戏崩溃。

### F03 — 旧版已修复：合法 LZMA 表会让游戏启动前失败

历史位置：1.1.5（`8b5c910`）的 `backend/start_options.py` 解压函数；1.1.6（`35c3fcc`）增加了 CA 的长度头、LZMA 属性和原始流支持。

使用一个合法的 PFH5 Mod Pack，压缩标记正确，内容是标准 CA LZMA 布局的 `main_units` 数据表。将 1.1.5 的实际解压函数接入相同的真实启动生成路径：

- 旧函数报 `unknown compression method`，API 返回错误，启动进程调用次数为 **0**。
- 当前函数正常解析同一文件，80 人单位生成 160 人，启动边界测试桩调用 **1 次**。

这能解释一类“1.1.6 以前、启用内置数据修改后游戏完全打不开”的反馈，其失败层是启动器解析数据，而不是证明 Data 中有两份文件导致游戏崩溃。没有玩家日志，无法确认具体反馈就是这一类。

## 代码检查的补充边界

`_stage_runtime_pack_in_data` 现在以 Data 根目录下的词法目标路径替换文件；遇到符号链接时，原子替换会替换链接自身，不跟随它改写外部目标。禁用时也只移除 Data 里的链接项。隔离用例模拟覆盖替换分支；本机真实创建 Windows 符号链接仍受 `WinError 1314` 限制。

未知表版本会被明确拒绝并中止启动，本轮版本 999 的样本启动调用数为 0。保留这样的拒绝有助于避免把无法解读的表写入游戏；不能为降低失败提示而静默吞掉错误或继续使用旧补丁。

## 复现与回归

在仓库根目录运行：

```powershell
python docs/audits/2026-10-03-runtime-packs/reproduce.py --assert-safe
python docs/audits/2026-10-03-runtime-packs/read_live_packs.py
```

第一条在修复前以退出码 **1** 稳定复现 `renamed_copy` 和 `unit_source_changes_during_build`。修复后两项都通过：改名副本不再参与加工或启动，单位数据补丁会用更新后的源 MOD 重建。其余检查也覆盖旧解压器和当前版本差异、五个标准生成名字的覆盖和禁用清理、写入中断时保留完整旧文件、无临时文件残留，以及未知版本阻止启动。真实 Windows 符号链接创建受权限限制时会在结果中标记跳过；同一替换逻辑另有单元测试。最新结果见 [reproduction.json](reproduction.json)。

第二条只读取真实输入，所有重建输出都在仓库临时目录；它依赖本机实际设置和现存的游戏数据补丁，属于该现场的回读工具，不是其他电脑均可直接运行的通用回归。

完整回归共 **518 passed, 1 skipped, 191 subtests passed**；前端 **302 passed**。后端测试进程把 `backend.api.is_game_running` 设为 False，以隔离本机正在运行的游戏；启动、进程状态调用在复现中使用测试桩。生产构建通过，保留现有的大型 JavaScript 分块提示。

本次版本修复了两项可复现的 Pack 风险和一个符号链接路径风险。F03 对应的 CA LZMA 支持已从 1.1.6 起存在。由于没有玩家失败日志或原始截图，仍无法判定已反馈的“游戏打不开”具体属于哪一类；必要时应结合 `app.log`、实际启动清单与游戏转储确认现场根因。
